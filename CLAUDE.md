## Project overview

This is a PreTeXt course project ("Calculus with Functions I", MATH 231), originally scaffolded with `pretext new course`. The course is assembled as a single PreTeXt `<book>` in `source/main.ptx`, which pulls in every other source file via `<xi:include>` and organizes them into chapters (`course-documents`, `course-objectives`, `activities`, `handouts`, `homework`, ...).

When a new activity or objectives file is added, `source/main.ptx` needs a corresponding `<xi:include>` added inside the relevant `<chapter>`. Follow the existing include list as the pattern; it's currently manually curated, in the order the files should appear.

## Activity (worksheet) design philosophy

Activities are built as `<worksheet>` documents, not full POGIL, though POGIL is the starting influence, so they can be printed with blank workspace for students to write in during class. The intended arc, in the instructor's own terms, is:

**exploration → generalization → naming the discovery → practice/challenge.**

In practice this plays out with real class-time constraints in mind:

- Full, unguided student discovery doesn't fit in a 50-minute period for this course. The realistic pattern is: groups work through the activity, the instructor facilitates a whole-class walkthrough of the first level of an idea to make sure the initial concept has landed, then groups apply that idea to a new question that introduces one necessary added wrinkle, and so on.
- This whole-class facilitation is a live teaching decision, not something encoded in the document structure. The `.ptx` source doesn't need to, and shouldn't try to, mark "this part is done together as a class" versus "this part groups do independently." That call is made in the room, activity to activity.
- **Time calibration:** design conservatively. Content that feels like roughly 30 minutes of material tends to fill the entire 50-minute period once whole-class discussion is folded in. Do not pad an activity assuming discussion time is separate from the content's own footprint. It isn't.

## Activity XML conventions

Based on the existing activities (e.g. `05-polynomial-sign-behavior.ptx`, `06-rational-sign-behavior.ptx`, `07-rational-inequalities.ptx`, `08-function-notation.ptx`):

- Root element is `<worksheet xml:id="activity-<descriptive-slug>">`. The `xml:id` is a descriptive slug naming what the activity is about (e.g. `activity-solve-rational-inequality`), not just a number. File names carry the numeric ordering prefix (e.g. `07-rational-inequalities.ptx`); the `xml:id` does not need to repeat it.
- A top-level `<introduction>` sets up the activity's premise before the first exercise.
- Each `<exercise>` represents one phase or "wrinkle" in the exploration → generalization → naming → practice arc, typically one step up in complexity from the previous exercise. Give each a `<title>` labeling its role in the sequence; the established pattern is `"Section N: <short description>"`.
- Within an `<exercise>`, the `<introduction>` is where formalization/naming happens. It's the connective tissue explaining the concept or process before the student is asked to apply it, and often where new vocabulary (`<term>`) is introduced.
- `<task>` elements are the sub-steps or sub-problems within a phase. A phase can be a single task or several tasks that vary a detail while reusing the same underlying setup (e.g. reusing a sign-analysis summary across three different inequality directions).
- `workspace` is set per `<exercise>`/`<task>` based on how much room the expected work actually needs. Observed values range from `0in`, when an exercise's own introduction carries the content and work happens inside its tasks, up to `2in` or more for open-ended work.
- Step-by-step instructions inside a `<statement>` are written as `<ul>`/`<ol>` lists of discrete steps, not as prose paragraphs.
- Inline markup conventions in use: `<m>`/`<md>` for math, `<term>` for first introduction of vocabulary, `<em>` for emphasis, `<q>` for quoted symbolic expressions referenced in prose (e.g. `<q><m>\ge 0</m></q>`).
- Diagrams needing custom figures (e.g. a piecewise graph with open/closed points) are built as `<figure>` containing `<image>` with a `<shortdescription>` and a `<latex-image>` holding raw tikz code, wrapped in `<![CDATA[ ... ]]>` to avoid XML-escaping issues with characters like `<` and `&`.

## Objectives file conventions

Based on `source/objectives/week-01-02.ptx`:

- Objectives are grouped into **two-week blocks matching the assessment cadence**, since assessments occur every two weeks. Each block is one file, one `<section xml:id="notes-week-NN">`, titled `"Week N and Week N+1"`.
- Within a section, each learning outcome gets its own `<subsection>`.
- Each subsection contains:
  1. An `<assemblage>` holding the outcome statement, phrased as an "I can..." statement describing what the student should be able to do.
  2. A "What do I need to understand?" bulleted list of key concepts required for success. Existing entries are often, though not rigidly, categorized by label, e.g. *Conceptual*, *Computational*, *Modeling*, but these categories should fit the outcome rather than being forced onto every subsection.
  3. A sample `<exercise>`, built where possible with the Runestone dynamic-exercise machinery so the problem is randomized and auto-checked: `<setup>` with `<de-object>`/`<de-random>`/`<de-expression>` defining randomized parameters and the correct answer, `<fillin>` for the student's response, and `<evaluation>`/`<mathcmp>` (or similar) for automatic checking.
- Interval/set-based sample exercises using `assets/code/btmIntervalSets.js` are still experimental. Treat that pattern as evolving, not a finished template.
