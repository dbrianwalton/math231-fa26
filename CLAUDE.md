## Project overview

This is a PreTeXt course project ("Calculus with Functions I", MATH 231-0002, Fall 2026), originally scaffolded with `pretext new course` (PreTeXt CLI 2.52.3, pinned in `requirements.txt`). The course is assembled as a single PreTeXt `<book>` in `source/main.ptx`, which pulls in every other source file via `<xi:include>` and organizes them into chapters (`course-documents`, `course-objectives`, `activities`, `handouts`, `homework`).

When a new activity or objectives file is added, `source/main.ptx` needs a corresponding `<xi:include>` added inside the relevant `<chapter>`. Follow the existing include list as the pattern. It is manually curated, in the order the files should appear. 

`project.ptx` defines the build targets (`course` for HTML, `print` for PDF, plus standalone `pdf`, `slides`, `slides-annotated`, and `scorm` targets). Claude does not change targets unless asked.

## Activity (worksheet) design philosophy

Activities are built as `<worksheet>` documents, not full POGIL, though POGIL is the starting influence, so they can be printed with blank workspace for students to write in during class. The intended arc, in the instructor's own terms, is:

**exploration → generalization → naming the discovery → practice/challenge.**

In practice this plays out with real class-time constraints in mind:

- Full, unguided student discovery doesn't fit in a 50-minute period for this course. The realistic pattern is: groups work through the activity, the instructor facilitates a whole-class walkthrough of the first level of an idea to make sure the initial concept has landed, then groups apply that idea to a new question that introduces one necessary added wrinkle, and so on.
- This whole-class facilitation is a live teaching decision, not something encoded in the document structure. The `.ptx` source doesn't need to, and shouldn't try to, mark "this part is done together as a class" versus "this part groups do independently." That call is made in the room, activity to activity.
- Splitting a group into two pairs that each do half of a comparison (for example, one pair computes `f∘g` and the other computes `g∘f`) is a pattern the instructor uses. It is written into the task text itself and given nested tasks, one per pair.
- **Time calibration:** design conservatively. Content that feels like roughly 30 minutes of material tends to fill the entire 50-minute period once whole-class discussion is folded in. Do not pad an activity assuming discussion time is separate from the content's own footprint. It isn't. When a draft looks long, offer specific tasks that could be trimmed.

## Activity XML conventions

Based on the existing activities (`02` through `12`; the most recent and most representative are `08-function-notation.ptx` through `12-inverse-functions.ptx`):

- Root element is `<worksheet xml:id="activity-<descriptive-slug>">`. The `xml:id` is a descriptive slug naming what the activity is about (e.g. `activity-function-composition`), not just a number. File names carry the numeric ordering prefix (e.g. `10-function-composition.ptx`); the `xml:id` does not repeat it. The next activity after `12` is `13`.
- The worksheet has a `<title>` and then a top-level `<introduction>` that sets up the activity's premise before the first exercise. Recent introductions are a paragraph or two of prose that say what the activity is about and why it matters for what comes next.
- Each `<exercise>` represents one phase or "wrinkle" in the exploration → generalization → naming → practice arc, typically one step up in complexity from the previous exercise. Give each a `<title>` labeling its role in the sequence; the established pattern is `"Section N: <short description>"`.
- From activity `08` onward, exercises and tasks carry `xml:id` attributes: exercises as `ex-<activity-topic>-<slug>` and tasks as `task-<slug>` (for example `ex-composition-eval` and `task-composition-eval-warmup`). Figures and images use `fig-<...>` and `image-<...>`. Follow this in new activities. Earlier activities (`02` through `07`) mostly lack these ids and need not be retrofitted unless asked. Ids must be unique across the whole book, so make the task slugs specific to the activity.
- Within an `<exercise>`, the `<introduction>` is where formalization/naming happens. It is the connective tissue explaining the concept or process before the student is asked to apply it, and often where new vocabulary (`<term>`) is introduced. Formal definitions may be set off in an `<assemblage>` with a `<title>` inside that introduction.
- `<task>` elements are the sub-steps or sub-problems within a phase. A phase can be a single task or several tasks that vary a detail while reusing the same underlying setup. A task may contain nested `<task>` elements (each with its own `<statement>` and `workspace`) when one prompt has parallel parts, such as the two-pairs split described above. When a task is a single problem, its `<statement>` holds the prompt directly.
- `workspace` is set per `<exercise>`/`<task>` based on how much room the expected work actually needs. Observed values range from `0in`, when an exercise's own introduction carries the content and work happens inside its tasks (this is the value on nearly every `<exercise>`), through `0.25in` to `2.5in` on tasks, with `1in`, `1.5in`, and `2in` the most common. A parent task whose nested tasks carry the work uses `0in`.
- Step-by-step instructions and multi-part prompts inside a `<statement>` are written as `<ul>`/`<ol>` lists of discrete steps, with each item's text wrapped in `<p>`, not as prose paragraphs.
- Inline markup conventions in use: `<m>`/`<md>` for math, `<term>` for first introduction of vocabulary, `<em>` for emphasis, `<q>` for quoted symbolic expressions or words referenced in prose (e.g. `<q><m>\ge 0</m></q>`).
- Display math uses `<md>` with `<mrow>` and `\amp` for alignment. Do not use `<me>` (it was deliberately removed from the project). Inside math, write `\lt` and `\gt` for strict inequalities and `\amp` or `&amp;` for alignment, so the XML stays valid.
- Tables use `<tabular>` with `<row>` and `<cell>`, inside a `<table>`/`<title>` when the table needs a caption (see activity `08`).
- Diagrams needing custom figures (e.g. a piecewise graph with open/closed points) are built as `<figure>` containing `<image>` with a `<shortdescription>` and a `<latex-image>` holding raw tikz code, wrapped in `<![CDATA[ ... ]]>` to avoid XML-escaping issues with characters like `<` and `&`. Images are typically `width="60%"`.
- Links to external tools (Desmos) are given with a QR-code image plus `<url href="..." visual="..."/>`, as in activities `05` and `06`.
- Check every formula and worked answer in a new worksheet for algebra and domain correctness before delivering it.

## Objectives file conventions

Based on `source/objectives/week-01-02.ptx` (fully developed), `week-03-04.ptx` (developed, static sample exercises), and `week-05-06.ptx` (a stub):

- Objectives are grouped into **two-week blocks matching the assessment cadence**, since assessments occur every two weeks. Each block is one file, one `<section>`, titled `"Week N and Week N+1"`, with a short `<introduction>` summarizing what those weeks covered.
- Within a section, each learning outcome gets its own `<subsection>` titled with the outcome code and name, for example `"P1 Linear Modeling"` or `"F1 Function Notation"`. Codes so far: `P1` to `P4` (weeks 1 to 4) and `F1` to `F3` (functions: notation, domain, deconstruction). Inverse functions (activity `12`) do not have an outcome yet.
- Each subsection contains:
  1. An `<assemblage xml:id="assemblage-<code>">` holding the outcome statement, phrased as an "I can..." statement describing what the student should be able to do. The assemblage `<title>` is just the code.
  2. A "What do I need to understand?" list of key concepts required for success, written as a `<p>` containing that question followed by a `<ul>`. Existing entries are often, though not rigidly, categorized by label, e.g. *Conceptual*, *Computational*, *Modeling*, but these categories should fit the outcome rather than being forced onto every subsection.
  3. A sample `<exercise label="<code>-<slug>">`. In `week-01-02.ptx` these are built with the Runestone dynamic-exercise machinery so the problem is randomized and auto-checked: `<setup>` with `<de-object>`/`<de-random>`/`<de-expression>` defining randomized parameters and the correct answer, `<fillin>` for the student's response, and `<evaluation>`/`<mathcmp>` (or similar) for automatic checking. In `week-03-04.ptx` the sample exercises are static (a `<statement>` only, some with a `<table>`). Ask which form is wanted when a new sample exercise is requested.
- Interval/set-based sample exercises using `assets/code/btmIntervalSets.js` are still experimental. Treat that pattern as evolving, not a finished template.
- Known inconsistencies in the current objectives files, to raise with the user rather than silently fix: the section `xml:id`s look off by one (`week-03-04.ptx` uses `notes-week-02` and `week-05-06.ptx` uses `notes-week-03`, while the titles say weeks 3 and 4, and weeks 5 and 6); the `P4` subsection is titled "Linear Modeling" although its outcome is about sign analysis of inequalities; and `week-05-06.ptx` has only the `F3` outcome with an empty "What do I need to understand?" and no sample exercise.
